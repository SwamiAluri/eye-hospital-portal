## 1. Search request generated by FE

**UI:** `CollectionWorkbench` — input `data-testid="collection-search"`, placeholder `"Search task number…"`.

**Exact value entered:** whatever the operator types into local React state `search` (string). On every `onChange`:

1. `setPage(1)`
2. `setSearch(e.target.value)` (raw input; trim happens only at API call time)

**API call:** `listLmsCollectionTasks({ search: search.trim() || undefined, status?, collectionBranchId?, page, pageSize: 25 })`  
**Client:** `apps/hospital-portal-web/src/lib/lms/lms-collection.api.ts` → `GET /lms/collection/tasks` with axios `params`.

**Is the value sent?** Yes, when non-empty after trim. Empty/whitespace → `search` omitted.

**Example URLs (axios → LaboratoryApi base includes `/api`):**

| Operator input | Query string |
|---|---|
| `COL-20261009-000003` | `GET /api/lms/collection/tasks?search=COL-20261009-000003&page=1&pageSize=25` |
| `col-20261009-000003` | `GET /api/lms/collection/tasks?search=col-20261009-000003&page=1&pageSize=25` |
| `000003` | `GET /api/lms/collection/tasks?search=000003&page=1&pageSize=25` |
| (whitespace only) | `GET /api/lms/collection/tasks?page=1&pageSize=25` (no `search`) |

Optional concurrent filters also serialize when not `all`: `status`, `collectionBranchId`.

**Reload trigger:** `load` is in `useCallback` deps `[canView, search, status, branchFilter, page]` and `useEffect` runs `load()` whenever those change — **every keystroke** issues a list request (no debounce).

**Does FE replace/clear results after search?** Yes: success → `setItems(result.items)`; error → clears to `[]`. While loading, table is replaced by “Loading collection queue…”. There is **no request-sequence / abort guard**, so out-of-order responses from rapid typing can overwrite a newer result with an older one (secondary UX risk, not the primary match bug).

## 3. Backend handling

**Service:** `CollectionService.ListAsync`

```csharp
if (!string.IsNullOrWhiteSpace(query.Search))
{
    var s = query.Search.Trim();
    q = q.Where(t => t.TaskNumber.Contains(s));
}
```

- Tenant filter always applied.
- Search applies **only** to `TaskNumber` (not `OrderNumber`, patient name/MRN, GUID id).
- Trim only; **no** `ToLower()` / culture normalize.
- Status / branch / orderId filters AND with search when supplied.

**Orders comparison (reference only; Orders unchanged):**

```csharp
var s = query.Search.Trim().ToLower();
q = q.Where(o => o.OrderNumber.ToLower().Contains(s));
```

Collection search is **not** aligned with Orders’ case-insensitive pattern.

## 4. Search database behavior

EF Core Npgsql translates `string.Contains(s)` to a PostgreSQL **case-sensitive** substring predicate (equivalent to `LIKE '%…%'` / `strpos`), not `ILIKE`.

**Live DB probes (2026-10-09) against `lms_collection_tasks`:**

| Predicate | Result |
|---|---|
| `task_number LIKE '%COL-20261009-000003%'` | **1** |
| `task_number LIKE '%col-20261009-000003%'` | **0** |
| `task_number ILIKE '%col-20261009-000003%'` | **1** |
| `task_number LIKE '%000003%'` | **1** |

**Matching semantics (implemented):**

| Dimension | Behavior |
|---|---|
| Mode | Substring **contains** (not exact-only, not prefix-only) |
| Case | **Case-sensitive** on PostgreSQL |
| Property | `TaskNumber` only |
| Exact known task (correct case) | **Matches** at DB |
| Exact known task (wrong case) | **Does not match** |
| Pagination | Applied after filter (`Skip`/`Take`); search change resets FE page to 1 — pagination does **not** hide a match on page 1 when total ≤ pageSize |

## 5. Search root cause (if broken)

Search is **not** a dead UI control: FE → API → `ListAsync` → DB filter are connected.

**Primary root cause of “search not working” under realistic UAT:**

1. **Case-sensitive `TaskNumber.Contains`** — typing or pasting lowercase / mixed-case task numbers yields empty queue, while the same value works case-insensitively on Orders.
2. **Search scope is task number only** — typing the visible **Order** number or patient text cannot match (UI shows Order/Patient columns beside Task).

**Secondary contributing factors (do not alone prove “broken wiring”):**

3. No debounce / stale-response guard → flicker or wrong list under fast typing.
4. Status/branch filters AND with search — e.g. status=`Planned` while searching a `Completed` task → empty (correct filter interaction, easy to misread as search failure).

**Exact known task number (correct case):** expected to work end-to-end for `COL-20261009-000003` / `COL-20261009-000004` when status/branch filters do not exclude them. Lowercase variant expected to fail today.

## 6. Claim behavior

| Aspect | Implemented behavior |
|---|---|
| Endpoint | `POST /api/lms/collection/tasks/{id}/claim` |
| Permission | `lms.collection.collect` |
| Actor | JWT user id only |
| Effect | Sets `ClaimedByUserId = actor`, `ClaimedAt = utc`; increments `RowVersion`; audits `CLAIM_COLLECTION_TASK` |
| Idempotent re-claim by same actor | Returns current detail (no-op success) |
| Other user’s claim | **409** `claim_conflict` |
| AssignedTo | **Ignored** — Claim does not read or clear `AssignedToUserId` |
| Status | Blocked only if terminal (`Completed` / `Cancelled`) via `EnsureNotTerminal` |
| Open/detail GET | Does **not** claim (PD-COL-16) |
| Create | Does **not** auto-claim creator |

**Scenario A — Unclaimed/unassigned → Claim:** Succeeds. `ClaimedByUserId = actor`. `AssignedToUserId` remains null.

## 7. Assign behavior

| Aspect | Implemented behavior |
|---|---|
| Endpoint | `POST /api/lms/collection/tasks/{id}/assign` |
| Permission | `lms.collection.manage` |
| Body | `AssignToUserId` + `ExpectedRowVersion` (+ optional idempotency) |
| Platform validation | `IPlatformReferenceClient.ValidateUserAsync(tenantId, userId)` → Auth `POST api/internal/lms/validate-user` |
| Effect | Sets `AssignedToUserId` / `AssignedAt`; does **not** set `ClaimedByUserId` |
| Conflict | **409** `assign_conflict` only when **reassigning** an already-assigned task **while** it is claimed by someone **other than** the actor |

**Conflict condition (verbatim logic):**

```text
AssignedToUserId already set
AND new AssignToUserId ≠ existing
AND ClaimedByUserId is not null
AND ClaimedByUserId ≠ actor
→ 409 assign_conflict
```

First-time assign while claimed by another user is **allowed**. Assign never clears claim.

## 8. Claim + Assign interaction (actual)

API **allows Claim and Assign to coexist** on the same task (two nullable columns). There is **no** single “owner” field and **no** rule that claim implies assignee or vice versa.

| Scenario | Actual implemented outcome |
|---|---|
| **A** Unclaimed/unassigned → Claim | Claim set to actor; Assigned null |
| **B** Claimed by User A → Assign to User B | **Allowed** for manage actor (including non-A), because either Assigned was null (first assign) or actor is claimer when reassigning. Result: **ClaimedBy=A and AssignedTo=B simultaneously** |
| **C** Assigned to User B → User A claims | **Allowed**. Claim ignores AssignedTo. Result: **ClaimedBy=A, AssignedTo=B** |
| **D** Claimed by User A → User A releases | Claim cleared; **AssignedTo unchanged** |
| **E** Assigned to User B → User A releases claim | If User A is **not** the claimer → **403** `release_forbidden`. If unclaimed → no-op success. **AssignedTo never cleared by Release** |

**Worklist UI:** ownership column shows `"Claimed"` if `claimedByUserId` is set, else `"Assigned"`, else `"Unclaimed"` — so when both are set, UI displays **Claimed** and hides Assigned.

**Status transition:** independent of claim/assign (no ownership gate on Planned→Ready→InProgress→Completed).

**Product docs:** PD-COL-16 chose hybrid shared queue + optional claim/assignment; leave/reassignment **out of first slice**. Implementation report documents claim conflict / release-own-claim but does **not** define authoritative precedence when both fields are set.

→ **PRODUCT DECISION REQUIRED** for Claim + Assign coexistence / precedence / whether Assign should clear or block Claim (and vice versa), and for manage-forced release/reassign (explicitly out of scope today).

## 10. Assignment authorization

| Threat | Blocked? | How |
|---|---|---|
| Actor without manage | Yes | `LaboratoryAuthz.CollectionManage` on Assign endpoint |
| Cross-tenant user id | Yes | Auth validate-user: `Users` where `Id == userId AND TenantId == X-Tenant-ID AND DeletedAt == null` → else 404 `user_not_found` → Laboratory maps to 400 `platform_not_found` |
| Inactive / invalid user | Yes | `UserStatus` must be `"active"` (case-insensitive) → else 400 `user_inactive` |
| Empty GUID | Yes | `assignee_required` |
| Soft-deleted user | Yes | `DeletedAt == null` filter |
| Arbitrary **active same-tenant** user | **Not blocked** | No check that assignee holds `lms.collection.collect` (or any collector role). Any active tenant user GUID that passes validate-user can be stored as `AssignedToUserId` |

Security conclusion for this slice: Assign is **not** open cross-tenant / inactive; it **is** open to any active user in the actor’s tenant. Tightening assignee eligibility would be a product/authz decision, not implemented today. **Authorization was not changed in this diagnostic.**
