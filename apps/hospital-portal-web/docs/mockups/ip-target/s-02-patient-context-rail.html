The whole answer for one patient without leaving the census. One component, four persona orderings. Persona controls section order and visibility only — never authorisation. The server stays the boundary; resolveIpPersona(permissions, roles) derives from permission codes with role strings as a fallback.

Removed from today’s PatientQuickPanel: MiniStepper (renders 5 steps for a 9-state machine, so ReadyForSurgery, SentToOT, PostOp and ReadyForDischarge are invisible) · AddTransactionForm (writes to the ip_billing_transactions projection, bypassing receipt numbering, idempotency, refund rules and the CCMS outbox) · three of four billing CTAs · 9–10 px type on clinical data · permission-code and OpdBill jargon · question-style headings.
The identification banner is the same for everyone. Persona changes which sections appear below it and in what order, but never the identity block: full name, UHID, age, sex, date of birth, alerts and the operating eye are identical for a cashier and a surgeon. Safety identifiers are not a matter of role. The one exception is the alert strip, which a cashier does not need and does not see, since allergy is clinical data with no bearing on taking a payment. See S-01 for the rationale and the full banner states.

Caching and accessibility

Caching 3

All three per-patient reads — gates, financial summary, preauth — move to react-query keyed on journeyId with a ~30 s staleTime, so re-selecting a row is free. Today they are uncached useEffect calls that refire on every click.

Docked semantics

Not a dialog. A landmark <aside> with aria-label, reachable in tab order after the table. No focus trap, because the list must stay usable alongside it.

Announcements

Selection changes announce the patient name in a live region. Blocker counts are text, never colour alone. 12 px minimum throughout, replacing today’s 9–10 px labels on clinical data.
