Three rules that every screen in this set follows, and the verified list of endpoints they are allowed to call. Section 3 was checked against the source — routes, tables and permission codes here are what exists in microservices/ip-management-service and microservices/auth-service today, not what the design wishes existed. Anything the design needs but the backend does not have is listed as a gap with the work item that closes it.

1. Every record a user can create has an Add action and a history

A panel that displays values but offers no way to create them is a read-only report pretending to be a workflow. Wherever the backend supports appending a row, the screen shows an Add control and, below it, the history of what has already been added — who, when, and from where.

The pattern

  1. Add control in the panel header, right-aligned, labelled with the noun: “Add observation”, not “+”.
  2. Focused dialog with only the fields the append needs.
  3. Server validates; the row is appended with actor and timestamp taken from the token, never from the form.
  4. History table refreshes and the new row is highlighted briefly.
  5. Correction follows the domain rule below — edit, append-a-correction, or not at all.

Where an Add is shown but no endpoint exists, the mockup marks the control Gap and the map row names the work item. It is not drawn as if it works. The largest of these is that most clinical form writes are not audited — journey_audit_log is written for journey lifecycle changes and two pre-op actions only, so a vitals correction currently leaves no audit row.

2. Messages are written for the person reading them

A status code, an exception name or a service name in front of a ward nurse is a defect. The message has to answer three things: what happened to my work, what do I do now, and only if asked, what does support need to know.

What the backend producesWhat the screen says
503 Service Unavailable from ip-management We couldn’t refresh the patient list. Showing what we had at 1:58 pm. Try again
409 Conflict on a payment This bill changed while you were typing. Another ₹10,000 was collected at 2:14 pm, so nothing is due now.
Idempotency key replay This payment was already recorded. Showing receipt RCP-20260824-00001188 — the patient was not charged twice.
InvalidOperationException: transition ReadyForSurgery → Admitted not allowed This can’t be undone now — the patient has already gone to theatre.
HARD_BLOCK: consent_unsigned Surgical consent isn’t signed yet. Open the consent step
Bill is finalized (is_locked = true) This bill is closed. To change it now, raise a credit note.
No variant mapping for SKU CTR-001 This item has no price set up yet, so it can’t be charged. Set up pricing
403 Forbidden — missing bill.update You don’t have access to collect payments. Ask an administrator, or send the patient to the cashier.
Auth billing client timeout Payments are temporarily unavailable. Nothing was charged — please don’t write a manual receipt. Try again

Always say what happened to the work

“Nothing was charged” and “your change wasn’t saved” are the most important words in a failure message. Without them staff invent a workaround, and at a cash counter the workaround is a handwritten receipt.

Put the fix in the message

Every blocking message carries the action that clears it as a link. A message that names a problem and leaves the user to find the screen is only half written.

Technical detail is opt-in

One Details for IT line, collapsed, carrying the correlation id and the raw response. That id is the only thing support actually needs, and it is what ties the screen to the audit row and the outbox event.

The IT-facing screens are the exception. On integration health (S-16) and reconciliation (S-15) the reader is the engineer, so event types, attempt counts and HTTP status are the content. Even there the headline is plain and the effect is named in money or patients, not in queue depth.

Success messages

Name the artefact

₹10,000 collected. Receipt RCP-20260824-00001188. Patient due is now ₹0.

The receipt number is what the patient leaves with, so it is the thing the message is about.

Confirm the consequence, not the API call

Observation recorded at 10:25 am. Three stable readings now — recovery criteria met.

“Saved successfully” tells the nurse nothing she did not already assume.
