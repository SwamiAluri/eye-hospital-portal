Visual companion to §20.4–§20.7 of docs/ip-ward-ot-billing-coverage-target-architecture.md. Every screen below carries its own data & action map resolving each interface element to API → backend service → database table → owning module → permission → event, so a mockup can be read as an implementation contract rather than a picture. These are static HTML: nothing here is wired to a running service, and no application code is changed by this folder.

How to read the maps. 1 markers point at a change to an existing element, 2 at something net-new, and 3 at a defect being corrected. The Owner column is the module that owns the write — it is the boundary that must not be inverted.
Start here: Conventions. It carries three things every screen depends on — the rule that any record a user can create has an Add control and a visible history, the copy rules that keep status codes and service names out of the user interface, and the verified list of endpoints, tables and permission codes read from ip-management-service and auth-service. That last section also lists what an earlier draft of these mockups got wrong, including a permission code and a concurrency mechanism that do not exist.
